# 그룹(멀티테넌시) 도입 검토

> 앱스토어/플레이스토어 정식 배포를 앞두고 "그룹" 개념을 도입하기 위한 방향성 검토 및 변경 규모 추정.
>
> **요구사항 요약**
> - 회원가입한 사용자는 가장 먼저 **그룹을 생성** → 그 그룹의 **어드민**이 된다.
> - 다른 멤버는 어드민의 **초대 링크(또는 그룹 검색)**가 있어야만 그룹에 가입한다.
> - **플랫폼 전체를 관리하는 슈퍼어드민**과 **그룹 내 어드민**이 필요하다.

## 1. 현재 구조 진단 — 왜 큰 변경인가

현재 앱은 **단일 테넌트**다.

- 모든 사용자가 **하나의 전역 식물 풀**을 공유한다 (`plants_select_all`, `users_select_all` 모두 `USING (true)`).
- 권한은 **전역 role(member/admin)** 하나뿐 — 그룹/조직 개념이 스키마 어디에도 없다.
- 담당자 드롭다운·대시보드는 앱 레벨에서 `assigned_user_id`로만 거를 뿐, **데이터 격리(isolation)는 없다.**

즉 이 요청은 단순 기능 추가가 아니라 **권한·데이터 모델 재설계(멀티테넌시 전환)**다.
다만 **아직 출시 전**이고 admin/settings/calendar/delegations가 대부분 TODO·미구현이라 마이그레이션할 기존 자산이 적어 **지금이 가장 싼 타이밍**이다.

## 2. 추정을 좌우하는 핵심 설계 결정

| 결정 | 옵션 | 영향 |
|------|------|------|
| **멤버십 모델** | (a) 1인 1그룹 (`users.group_id`) vs (b) 다대다 (`group_members` + 활성 그룹 전환) | **가장 큰 변수.** (b)는 RLS·컨텍스트·그룹 스위처 UI 추가로 공수 1.5~2배 |
| **초대 방식** | (a) **초대 코드**(앱에 입력) vs (b) 초대 **링크**(딥링크) vs (c) 그룹 검색+가입요청 | (b)는 **Universal/App Links 네이티브 설정** 필요 — OTP로 일부러 피했던 딥링크 인프라가 부활. (c)는 검색·승인 플로우 추가 |
| **역할 체계** | 전역 role → **그룹별 role**(group_admin/member) + **플랫폼 슈퍼어드민** 분리 | 기존 `*_admin` RLS 정책 전부 재해석 |
| **슈퍼어드민 구현** | RLS 우회(service-role API) vs RLS 정책에 슈퍼어드민 분기 | 별도 관리 화면·API 표면 추가 |

**권장 기본값**: 멤버십은 다대다(`group_members`)로 설계하되 MVP는 단일 활성그룹, 초대는 **코드 방식**(딥링크 회피, OTP 결정과 일관), 슈퍼어드민은 **service-role 기반 별도 admin API**.

## 3. 변경 영역별 작업 + 규모

### A. DB / 스키마 / RLS — 🔴 가장 큰 덩어리 (위험도 최상)
- 신규 테이블: `groups`, `group_members`(user_id, group_id, role), `group_invites`(code, group_id, role, expires_at, used_by)
- 컬럼 추가: `plants.group_id`(+ FK/인덱스), 선택적으로 watering_logs/status_logs에도 group_id(RLS 성능용)
- `users.role` → 그룹별로 이전, `is_super_admin` 추가
- **RLS 전면 재작성**: plants·seasonal_presets·watering_logs·status_logs·delegations·users 의 모든 정책을 "요청자가 해당 행의 group 멤버인가" 기준으로 재정의. delegations는 "동일 그룹 내"로 제약.
- 트리거 수정(가입 시 그룹 미지정 허용), 기존 데이터 → 기본 그룹 시드
- **추정: 신규 마이그레이션 4~6개, 기존 정책군 7개 테이블 전부 재작성**

### B. 백엔드 API
- 신규: 그룹 생성, 초대 발급/수락, 멤버 목록/역할변경/추방, (슈퍼어드민) 그룹 관리 → **신규 라우트 ~6–8**
- 수정: `plants/*`, 담당자 users 조회, delegations 에 group scope → **기존 라우트 ~5 수정**

### C. 인증 / 컨텍스트 / 라우팅 가드
- `AuthProvider`에 그룹 컨텍스트(+ 다대다면 활성 그룹) 추가
- **온보딩 가드**: 로그인 후 그룹 없으면 "그룹 생성 / 초대코드 가입" 화면으로 강제 (middleware 또는 (main) layout)

### D. UI / Views
- 신규: 온보딩(생성/가입), 그룹 관리(멤버·초대), (다대다면) 그룹 스위처, 슈퍼어드민 화면 → **신규 뷰/위젯 ~4–6**
- 수정: 담당자 드롭다운 그룹 필터, 대시보드, 헤더 → **기존 ~4 수정**

### E. 네이티브 (초대를 "링크"로 할 때만)
- iOS `apple-app-site-association`, Android `assetlinks.json`, deep link 핸들링 → **초대 코드 방식이면 0**

### F. 테스트
- **멀티테넌시 격리(누수 방지) RLS 테스트**가 필수 (보안 핵심) + API/유닛

## 4. 종합 추정

- **전체 규모: Large** (사실상 권한·데이터 모델 재설계).
  - 단일그룹 + 초대코드 MVP: **Medium–Large**
  - 다중그룹 + 링크초대 + 슈퍼어드민 풀세트: **Large–XL**
- **가장 비싼 3곳**: ① RLS 전면 재작성 + 격리 검증, ② 온보딩 플로우/가드, ③ 슈퍼어드민 표면.
- 대략 영향 파일: **신규 ~20개 내외(마이그레이션·API·뷰·테스트), 기존 수정 ~15개**.

## 5. 리스크
- **테넌트 데이터 누수**가 최대 보안 리스크 — 한 테이블이라도 RLS 빠지면 교차 그룹 노출. 모든 테이블 일관 적용 + 격리 테스트 필수.
- **초대 링크 = 딥링크 인프라** 재도입 (OTP로 피했던 것). → 초대 코드 권장.
- 슈퍼어드민의 RLS 우회 경로는 service-role 키 취급 주의.

## 6. 권장 단계적 도입
- **Phase 1 (출시 MVP)**: groups + group_members + 단일 활성그룹 + **초대 코드** + group 기반 RLS + 온보딩 가드 + 그룹 관리 기본.
- **Phase 2**: 슈퍼어드민, 다중 그룹 + 스위처
- **Phase 3**: 그룹 검색 + 가입 요청/승인
